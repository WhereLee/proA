## 选题 A｜智能工单处理 Agent

### 一句话定位

用户用自然语言提需求或报问题（"帮我把上周的发票退掉""这个订单一直没发货"），Agent 理解意图 → 调用后台系统 API → 多轮确认 → 执行并回报。

### 为什么它能承载工程化

- **多步**：意图识别 → 只读查询 → 参数组装 → 人工确认 → 写操作执行 → 通知 → 回报，天然多阶段。
- **有状态**：工单本身是状态机（待受理 / 执行中 / 待确认 / 已执行 / 失败 / 已取消）。
- **副作用**：改订单状态、发通知、退发票——写操作会产生真实副作用，是"执行"而非"回答"。
- **失败路径**：工具调用失败、权限不足、确认被拒、执行中途崩溃需回滚或补偿。

### 目标与价值

- 中小厂最典型的真实需求：把"客服/运营手工操作系统"变成"对话式自动处理"。
- 后端含量最高：权限模型、状态机、事务、异步、审计都能真正用上。

### 核心功能（功能纵深，非排期）

**MVP**
- 意图识别 + 工具选择（function calling）
- 只读工具（查订单 / 查工单 / 查用户）
- 多轮对话与上下文维护
- 回答附操作依据（引用了哪条订单 / 哪个规则）

**V1**
- 写操作 + **危险动作人工确认（HITL）**，确认记录持久化
- 工具白名单 + 参数 **schema 级校验**（拒绝模型裸拼参数）
- 工具权限分级（不同角色可调用的工具集不同）
- 写操作**幂等键**，避免重试/恢复时重复产生副作用

**V2**
- 工单**状态机** + checkpoint **断点续跑**（进程崩溃可从最近一步恢复）
- 失败路径策略：重试上限 / 退避 / 降级 / 挂起转人工 / 失败终止
- 全链路 trace + 成本统计 + 操作审计
- Eval：任务级数据集（输入 → 期望最终状态），规则断言优先

### 系统架构（组件与数据流）

```
Client
  └─> FastAPI (SSE 流式接口)
        └─> Agent Runtime (自研最小 loop，另用 LangGraph 实现一份对照)
              ├─ LLM Provider（主/备模型，超时·重试·降级）
              ├─ Tool Registry（白名单 + schema 校验 + 权限）
              ├─ HITL 确认服务（挂起 → 通知 → 决策 → 恢复）
              ├─ State Store / Checkpointer（Postgres）
              └─ Trace / Cost（Langfuse 或自建）
        └─> 业务 Mock 服务（订单 / 工单 / 通知，供工具调用，可控注入故障）
```

> 关键：**业务系统要自己 mock**，且要能人为注入超时、报错、部分成功等故障，否则无法演练失败路径。

### 技术栈

Python · FastAPI · Postgres · Redis · LLM function calling · LangGraph（对照）· Langfuse · promptfoo · Docker

### 关键工程点（天然落地的检查项）

- P0：工具白名单与参数校验、危险操作 HITL + 审计、写操作幂等、任务状态机、checkpoint 与断点续跑、失败路径策略、prompt injection 防护、租户/会话隔离、SSE 流式、结构化输出与解析修复、超时/重试/降级、Eval 与回归门禁、全链路 trace、成本熔断。
- P1：HITL 完整审批闭环、MCP（把工具暴露为 MCP server）、上下文工程。

### 天然会踩的坑（面试可讲）

1. 模型编造工具参数 / 调错工具 → schema 校验 + 纠错重试。
2. 高危操作被误触发 → 分级 + 强制确认。
3. 工具返回值里藏 prompt injection → 视工具返回为不可信输入。
4. 多轮上下文错乱 / 意图漂移 → 会话状态与意图锁定。
5. 重试或恢复导致写操作重复执行 → 幂等键设计（恢复设计里最难的含金量点）。

### 验收标准（示例，最终以检查清单自检表为准）

- 任意一次 run 可回放完整 trace，定位到具体失败步骤。
- 危险操作 100% 经确认，确认记录可审计。
- 进程在写操作执行中被 kill，重启后不产生重复副作用。
- 给定 50–100 条任务级数据集，端到端成功率与关键状态断言可通过阈值门禁。

### 难度与风险

- 难度：中。
- 风险：业务系统需自建，工具集越多越像"造后台"；需克制范围，聚焦 2–3 类真实工单场景。

## 选题 B｜数据分析 Agent（Text-to-SQL / 代码执行）

### 一句话定位

用户上传 CSV 或连数据库，用自然语言提问（"上季度哪个区域复购率最高，画个图"），Agent 生成 SQL/代码 → 沙箱执行 → 校验结果 → 给出结论与图表。

### 为什么它能承载工程化

- **多步**：理解 Schema → 生成 SQL/代码 → 沙箱执行 → 报错自愈 → 结果校验 → 呈现。
- **有状态**：分析会话多轮追问，需记住数据集、前序结论、已用过的查询。
- **副作用**：默认只读，副作用弱——**需刻意加一个"写"路径**（导出文件 / 落库分析结果 / 发送报告）来满足"真实执行"要素。
- **失败路径**：SQL 报错、超时、空结果、结果明显异常，是天然的失败演练场。

### 目标与价值

- 技术深度最足，后端含量很高：沙箱、并发、资源限制、结果校验。
- "懂 AI 的后端"最佳证明之一，后端岗与 AI 岗通吃。

### 核心功能

**MVP**
- Schema 理解与 SQL 生成
- 只读执行 + 结果表格呈现
- 多轮追问

**V1**
- **执行报错自愈循环**（把 DB 错误回灌给模型重新生成，设重试上限）
- **代码执行沙箱**（容器 / 受限子进程，禁网、限内存与超时、只读挂载）
- **结果自检**（行数/量级/空值合理性校验，异常时不硬答）
- 自动图表生成

**V2**
- 复杂多表 / 多库、数据分析计划分解
- Eval：以"结果断言"为主的评分器（预期数值 / 结构校验），规则优先
- 成本与并发治理、全链路 trace

### 系统架构

```
Client
  └─> FastAPI
        └─> Analysis Agent（自研 loop + LangGraph 对照）
              ├─ LLM（NL → SQL / Python）
              ├─ Sandbox Executor（隔离容器，资源与网络受限）
              ├─ Result Validator（结构 / 量级 / 空值 断言）
              └─ Trace / Cost
        └─> DuckDB / Postgres（只读账号）
```

### 技术栈

Python · FastAPI · DuckDB / Postgres（只读）· 沙箱（容器优先）· LLM · plotly/matplotlib · Langfuse · promptfoo · Docker

### 关键工程点

- P0：安全（沙箱隔离、只读权限、危险 SQL 拦截）、结构化输出与解析修复、失败路径策略、超时/重试/降级、Eval 与回归门禁、全链路 trace、成本熔断。
- P1：上下文工程（大表 Schema 裁剪）、Agent 压测（并发执行资源占用）。

### 天然会踩的坑

1. SQL 幻觉 / 语法错 → 错误回灌重试。
2. 危险操作（DROP / 全表扫描）→ 沙箱 + 只读 + 语句白名单。
3. 沙箱逃逸 / 资源耗尽 → 隔离与资源上限。
4. 算错了还很自信 → 结果自检 + 置信度门控，宁可说"结果异常"。
5. 大表 / 复杂查询性能 → 限制扫描范围、加超时。

### 验收标准（示例）

- 沙箱无法访问网络、无法越出工作目录、超时自动终止。
- 错误 SQL 在 N 次重试内自愈，超过上限正确失败而非硬答。
- 结果校验能识别并拦截空结果 / 量级异常。
- 结果断言型评测集可通过阈值门禁。

### 难度与风险

- 难度：中高。
- 风险：沙箱安全是自己的坑，做浅了只是"eval 执行"（危险）；做深了是加分项，但要花时间。

### Agent 味偏淡的说明

数据分析 Agent 的"自主规划"较弱（多为固定流水线），偏向"代码工具链"。若想强化 Agent 感，可加入**分析计划分解**（多步：拆解指标 → 分步查询 → 汇总）。

## 选题 C｜行业调研报告 Agent

### 一句话定位

输入调研主题（"调研国产大模型在企业客服场景的应用现状"），Agent 自主拆解子问题 → 多轮搜索与抓取 → 去重归纳 → 生成带来源的 Markdown 报告。

### 为什么它能承载工程化

- **多步**：规划 → 检索 → 抓取 → 提炼 → 交叉验证 → 撰写，是最典型的 Plan-and-Execute。
- **有状态**：长任务，中间结果需持久化并支持断点续跑。
- **副作用**：弱——**必须刻意加"写"路径**（保存报告到库 / 发送 / 生成文件），否则只是"回答"，不满足"真实执行"。
- **失败路径**：抓取失败、超时、信息矛盾、跑飞/死循环，天然存在。

### 目标与价值

- Agent 自主味最足，最能体现 planning / 工具编排 / 长任务管理。
- 评估难度最高，做出可信效果最有说服力，但失败风险也最大。

### 核心功能

**MVP**
- 任务规划与子问题分解
- 搜索 + 抓取工具
- 分阶段总结 → 带来源报告

**V1**
- **异步队列 + 进度反馈**（长任务不阻塞，前端可看到阶段）
- **断点续跑**（checkpoint，抓取中断可续）
- 中间结果压缩 / 去重（防上下文爆炸）
- 步数上限与死循环检测

**V2**
- 多源交叉验证与事实核对（矛盾信息标注）
- Eval：报告质量（LLM-as-judge，固定评审 prompt + 双评）与结构断言并重
- 成本与并发治理、全链路 trace

### 系统架构

```
Client
  └─> FastAPI（提交任务 → 返回 task_id）
        └─> Task Queue（Redis + Celery/RQ）
              └─> Research Agent（规划 → 工具 → 撰写）
                    ├─ Search Tool / Fetch Tool（含重试与超时）
                    ├─ Context Compressor（分阶段摘要）
                    └─ Checkpointer（断点续跑）
        └─> 进度查询接口 / SSE
```

### 技术栈

Python · FastAPI · Redis + Celery/RQ · 搜索/抓取（httpx / playwright）· LLM · Langfuse · promptfoo · Docker

### 关键工程点

- P0：状态机、checkpoint 与断点续跑、失败路径策略、超时/重试/降级、结构化输出与解析修复、Eval 与回归门禁、全链路 trace、成本熔断；队列与限流。
- P1：上下文工程（history 压缩 + 效果验证）、memory 分层、Agent 压测、MCP。

### 天然会踩的坑

1. 跑飞 / 反复搜索同一问题 → 步数上限 + 终止条件 + 重复度检测。
2. 上下文爆炸 → 分阶段摘要、中间结果落盘而非全塞进 prompt。
3. 长任务超时 / 部署重启 → 异步队列 + checkpoint 续跑。
4. 抓到过时 / 矛盾信息 → 多源交叉验证 + 标注不确定性。
5. 成本不可控 → 明确预算上限与熔断。

### 验收标准（示例）

- 任务可在进程重启后从最近 checkpoint 续跑并完成。
- 单任务步数与 token 有硬上限，超限正确终止并说明。
- 报告可追溯到每条结论的来源链接。
- 报告质量评测集（LLM-judge + 结构断言）可通过阈值门禁。

### 难度与风险

- 难度：高。
- 风险：**最容易做成"看起来很酷的 demo"**——评估主观、稳定性难控。选它必须有把握把长任务与评估落地，否则落回三件套。

## 选择建议

结合"Java 出身、目标后端 / 全栈 / AI Agent 应用开发"的背景：

- **首选 A**：场景真实、坑多、后端含量最高、中小厂最买账，能自然带出权限 / 可观测 / 评估等加分项，且不需要重度安全沙箱。
- **次选 B**：若想突出技术深度与"后端 × AI"，且愿意在沙箱安全上投入，选 B。
- **谨慎选 C**：Agent 味最足、最能讲故事，但稳定性与评估最难，必须确保能落地长任务与评估，否则易滑回 demo。
