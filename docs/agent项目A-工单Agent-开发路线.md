## 使用约定

1. **阶段之间的顺序是有意义的**：地基（阶段 0）→ 只读闭环（1）→ 写操作与安全（2）→ 恢复（3）→ 评估与治理（4）→ 加分项（5）。不要跳阶段堆功能。
2. 每阶段的"验收标准"是**退出条件**，不达标不进下一阶段。
3. 每阶段都必须能跑通端到端，不留半成品分支。
4. 检查项编号（P0.x / P1.x）沿用《方向与检查清单》。

## 一、定位与边界

### 一句话

用户以自然语言提交售后/运营诉求，Agent 理解意图、查询后台系统、在危险动作前请求人工确认、执行写操作并回报；全流程可观测、可评估、可恢复、可审计。

### 做什么

- 2–3 类真实工单场景的端到端处理（见第二节）。
- 单 Agent + 工具 loop（**不默认上多 Agent**，除非出现明确的权限/上下文隔离理由）。
- 完整工程治理层：权限、状态机、checkpoint、HITL、审计、trace、成本、eval。

### 不做什么（防止范围失控）

- 不做真实电商/ERP 对接，业务系统全部自建 mock。
- 不做前端复杂 UI，够用即可（对话 + 确认 + trace 查看）。
- 不做多 Agent 编排、不做微调、不做多模态（属 P2，本阶段明确不做）。
- 不做通用"什么工单都能处理"——**聚焦少量场景做深**，比广度重要。

## 二、业务场景与 Mock 系统设计

### 选取的场景（建议 3 个，覆盖只读/写/高危写三档）

| 场景 | 类型 | 步骤 | 涉及的坑 |
|---|---|---|---|
| 查物流 / 催发货 | 只读 | 解析单号 → 查订单 → 查物流 → 汇总 | 意图识别、多轮补全 |
| 修改收货地址 | 写（有规则） | 查订单 → 校验时效/状态规则 → 确认 → 更新 → 通知 | 规则校验、HITL、幂等 |
| 申请退款 | 高危写 | 查订单 → 校验退款资格 → 计金额 → 确认 → 发起退款 → 通知 | 高风险确认、幂等、部分失败补偿 |

### Mock 服务（关键：必须能注入故障）

- `order-service`：查订单、改地址、退款。
- `ticket-service`：建单、查单、转人工。
- `notify-service`：发短信/站内信。
- `user-service`：查角色与权限。
- **故障注入开关**：超时、5xx、部分成功（退款成功但通知失败）、重复请求——用于演练失败路径与幂等，是后期恢复与 eval 的必备前提。

> 设计原则：mock 系统要**有真实业务规则**（如"已发货不允许改地址""超过 7 天不可退"），规则本身是 Agent 需要查询和遵守的知识，也是测试用例的来源。

## 三、模块划分与目录结构

```
agent-ticket/
  app/
    main.py                 # FastAPI 入口
    api/                    # 路由：对话、确认、任务查询、SSE
    agent/                  # agent loop / planner / 终止判定
    tools/                  # tool registry、schema、权限、幂等
    hitl/                   # 确认服务：挂起→通知→决策→恢复
    state/                  # 任务状态机、checkpointer、恢复逻辑
    llm/                    # provider 封装：超时/重试/降级/结构化输出
    security/               # injection 防护、参数校验、脱敏
    obs/                    # trace、成本统计、熔断
    eval/                   # 数据集加载、评分器、runner
    models/                 # DB models
  mocks/                    # 4 个业务 mock 服务 + 故障注入
  migrations/
  eval/
    datasets/               # 任务级数据集（json/yaml）
    graders/                # 规则评分器 + LLM-judge
  tests/
  docker/
  docs/
```

**自研 harness 对照**（检查清单主张一）：`app/agent/` 下用自研 loop；另建 `harness_langgraph/` 用 LangGraph 实现同一批工具与状态，用同一批 eval 数据对比。这是后期加分项，阶段 1 先不建。

## 四、分阶段路线

### 阶段 0｜地基与 Mock（"能跑通骨架"）

**目标**：端到端骨架打通，业务 mock 可控，LLM 集成基本功到位。

**交付物**
- FastAPI 骨架 + SSE 流式接口。
- 4 个 mock 服务 + 故障注入开关。
- LLM provider 封装：超时、重试、退避、主备模型降级（P0.5）。
- 结构化输出（JSON schema）+ 解析失败修复链路（P0.5）。
- trace 接入（Langfuse 或自建），每次 run 可回放。
- 容器化 + 一页启动文档（P0.5）。

**对接检查项**：P0 LLM 集成基本功、SSE 流式与中断、结构化输出、超时/重试/模型降级、容器化部署与文档。

**验收标准（退出条件）**
- 单轮只读问答可端到端返回，且为流式。
- 故障注入可稳定复现超时/5xx/部分成功。
- 任一次 run 能在 trace 中看到完整输入输出与耗时。

---

### 阶段 1｜只读闭环 + 工具治理（MVP）

**目标**：Agent 能正确选择工具、校验参数、查询并汇总，多轮可补全信息。

**交付物**
- agent loop：LLM → 工具解析 → 执行 → 结果回填 → 终止判定。
- tool registry：白名单 + schema 级参数校验（拒绝模型裸拼参数，P0.4）。
- 只读工具集（查订单/物流/工单/用户）。
- 多轮会话与上下文管理、会话隔离（P0.4）。
- 首批任务级 eval 数据集（≥50 条）+ 规则评分器，建立**基线指标**。

**对接检查项**：P0 工具白名单与参数校验、租户/会话隔离、Eval 数据集与评分器、全链路 trace。

**验收标准**
- 三类场景中的只读场景，端到端成功率达标（自定阈值，如 ≥90%）。
- 非法/幻觉参数被校验拦截而非直接透传。
- 会话间数据不可越权访问（有测试用例证明）。

---

### 阶段 2｜写操作 + 安全 + 幂等（分水岭）

**目标**：Agent 能安全地产生副作用。

**交付物**
- 写工具（改地址、退款）+ **幂等键**设计（P0.3）。
- **危险操作 HITL**：触发条件 → 挂起 → 通知 → 人工决策 → 恢复；确认记录持久化可审计（P0.4）。
- 工具权限分级（按角色限定可调用工具，P0.4）。
- prompt injection 防护：将工具返回值/外部数据视为不可信输入（P0.4）。
- 密钥管理 + trace 脱敏（P0.4）。

**对接检查项**：P0 写操作幂等、危险操作 HITL + 审计、工具白名单、prompt injection 防护、密钥管理与 trace 脱敏、租户/会话隔离。

**验收标准**
- 高危操作 100% 经确认，无确认不执行；确认记录可回溯。
- 对写操作重复发送（模拟重试）不产生重复副作用。
- 注入用例（工具返回中夹带恶意指令）无法诱导越权调用。

---

### 阶段 3｜状态机 + 断点续跑（可靠性）

**目标**：任务失败/崩溃可恢复，不产生重复副作用。

**交付物**
- 显式任务状态机（待执行/执行中/待确认/失败/完成/已取消），禁止隐式状态（P0.3）。
- checkpoint 机制：每步中间状态可序列化、可恢复（P0.3）。
- 断点续跑：进程崩溃/重启后从最近 checkpoint 继续（P0.3）。
- 失败路径策略文档 + 实现：每类失败的处理方式（重试上限/退避/降级/挂起转人工/失败终止，P0.3）。

**对接检查项**：P0 任务状态机、checkpoint 与断点续跑、失败路径策略、写操作幂等（在恢复场景下验证）。

**验收标准**
- 在写操作执行中途 kill 进程，重启后任务可继续且**无重复副作用**（有演练记录）。
- 每类失败都有明确策略并可通过故障注入触发验证。

---

### 阶段 4｜评估、治理与压测（施工验收）

**目标**：能证明"变好了"，能扛住并发与成本。

**交付物**
- Eval 体系完善：任务级数据集扩充、规则评分器 + LLM-judge（固定评审 prompt + 温度 0 + 双评）、失败样例按原因分类（P0.1）。
- **回归门禁**：改动 prompt/模型/图结构后指标过阈值才可合并，接 CI（P0.1）。
- 成本统计 + 预算上限 + 超限熔断（P0.2）。
- Agent 压测：并发 run 下的队列调度、模型限流触发点、延迟 P50/P95/P99、成本（P1.5）。
- 限流与并发闸门（P0.5）。

**对接检查项**：P0 Eval 与回归门禁、错误分析与失败分类、成本统计与熔断、限流与并发闸门；P1 Agent 压测。

**验收标准**
- CI 上回归门禁真实生效（构造一次"劣化改动"应被拦截）。
- 单 run 超预算自动熔断，有记录。
- 有延迟与成本的压测报告（含触发模型限流的临界点）。

---

### 阶段 5｜加分项（P1，按时间取舍）

**交付物**
- **自研 harness 对照**：同一批 eval 在自研 loop 与 LangGraph 实现上跑对比，产出结论（检查清单主张一）。
- MCP：把工具集暴露为 MCP server（P1.1）。
- 上下文工程：长任务 history 压缩 + 压缩后关键信息不丢的验证（P1.2）。
- HITL 审批闭环完善（P1.3）。

**验收标准**
- 有"自研 vs 框架"的客观对比数据与结论。
- 压缩前后关键信息留存有测试证明。

## 五、Eval 体系设计（贯穿全程）

- **数据集形态**：任务级，`{task_id, 用户输入, 期望最终状态, 期望关键工具调用轨迹}`，起始 50–100 条，随阶段扩。
- **评分器优先级**：规则断言优先（零成本、稳定）——最终状态断言、工具轨迹断言、必填字段校验；质量类主观维度用 LLM-judge，并定期人工抽检校准。
- **错误分类**：检索失败 / 工具选择错误 / 参数错误 / 规划错误 / 格式错误 / 模型能力，失败样例必须归类，否则 eval 只是数字。
- **门禁**：接入 CI，阈值未过不得合并。

## 六、风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 范围膨胀（想覆盖所有工单） | 每个都做不深 | 锁定 3 个场景，明确"不做什么" |
| 业务 mock 太假 | 无法演练真实失败 | mock 含真实业务规则 + 故障注入 |
| 只做 happy path | 退化为三件套 | 每阶段强制失败用例，阶段 3 为核心 |
| 沙箱/权限过度设计 | 拖慢主线 | 权限先做工具级，细粒度后置 |
| 幂等与恢复复杂 | 最容易翻车 | 阶段 3 单独攻坚，写操作先设计幂等键 |
| 评估主观化 | 无法证明效果 | 规则断言优先，LLM-judge 仅补主观维度 |
